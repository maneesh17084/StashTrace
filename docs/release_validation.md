# Release validations

Each row of the release checklist, with where it is proved and how to re-run it. Numbers for the
full dataset are in [full_run.md](full_run.md).

| Area | Evidence | Re-run |
|---|---|---|
| Data integrity | `tests/test_import_rules.py`: duplicate event IDs (DUPLICATE / CONFLICT), unknown store/SKU/actor/shift/source document, bad ID formats, unsupported movement type, missing and invalid adjustment reasons, role assignments outside their effective dates, self-approval, cross-store approver, return disposition and original-sale checks. Every rejection test asserts that stock and the ledger are unchanged. `validate.py` (database): "quarantined/duplicate/conflict rows never reach the ledger", "every ledger row traces to a POSTED import row", "every posting's actor role was effective at the event time and store". | `py -3.11 -m pytest tests/test_import_rules.py`; `py -3.11 -m data_tools.validate --data data/full --db var/full.db` |
| Arithmetic | `validate.py`: ledger rebuild equals cached `stock_balance` for every store/SKU; every current reconciliation recomputes from the ledger at its watermark; CHECK constraints enforce the stock equation on every row. `evaluate.py`: reconciliation `expected_qty` equals the generator's independently simulated ledger for every count. Tests: worked example 79/−5, "count never posts stock", "transfer in transit is not a loss at either end", transit write-offs have no stock effect. | `py -3.11 -m pytest tests/test_reconciliation_detection.py` |
| Retry and concurrency | Replaying a whole batch gives all DUPLICATE with identical movement IDs. Detection rerun gives 0 new cases. 20 threads post to the same store/SKU: all posted, balance exact, no lock errors. A failure forced after the ledger insert inside the transaction leaves no movements, results, keys or balance change; the retry posts exactly once and a second retry processes 0 rows. The worker re-queues failed jobs (max 3 attempts), and `POST /imports/{id}/retry` resumes. | `py -3.11 -m pytest tests/test_security_workflow.py tests/test_import_rules.py::test_idempotent_replay_and_conflict` |
| Access control | A store-2 manager gets 404 on store-1 reconciliation, alert and case IDs; 403 on store-1 filters for reconciliations and movements; 403 on CSV export for store 1; only own-store rows in alert lists and the dashboard. Cannot submit counts or post case events for store 1. A store-scoped uploader's rows for other stores are quarantined. Clerks and analysts cannot assign; store managers cannot resolve; LP cannot approve a write-off; store-scoped users cannot start detection. | `py -3.11 -m pytest tests/test_security_workflow.py tests/test_end_to_end.py` |
| Rule boundaries | Shortages of 4 / 5 / 6 against a 5-unit threshold give no alert / alert / alert. Benign cases not flagged: approved damage plus restocked and disposed returns, transfer in transit, transit loss written off once, late movement resolved by re-versioning, shortage explained by a quarantined row. Two discretionary adjustments are under the pattern threshold; three trip it. | `py -3.11 -m pytest tests/test_reconciliation_detection.py` |
| Traceability | Every alert stores rule code and version, threshold, observed value, calculation JSON, first run ID, and evidence rows linking movements, counts, reconciliation versions, import rows and transfer lines. The alert detail screen links back to each. Every case event stores actor, the role that authorised it, timestamp, decision, reason and any write-off movement. `validate.py` checks that every alert has a rule version, run, case and evidence, and that case state equals its last event. | `py -3.11 -m pytest tests/test_reconciliation_detection.py::test_every_alert_traces_to_rule_run_and_sources` |
| Detection quality | Precision, recall and false-positive rate per rule at the correct grain against held-out labels, with missed planted cases and flagged benign cases broken down by scenario. | `py -3.11 -m data_tools.evaluate --data data/full --db var/full.db` |
| Performance and operations | Full-volume import time and detection duration (`data/full/load_report.json`); p50/p95 API latency on the full database (`docs/performance.md`). Request IDs and timing in response headers and access logs; batch and run IDs in worker logs; `/api/v1/health` reports queued and failed jobs. Online backup + restore with integrity, FK and checksum comparison (`docs/backup_restore.json`). | `py -3.11 -m data_tools.perf --db var/full.db --data data/full`; `py -3.11 -m data_tools.backup_restore --db var/full.db --backup var/backup/full.db` |
| Frontend | Headless Chrome drove login, dashboard, alert queue and detail, reconciliation list and detail, import list and detail, case list, assignment through the form, and count entry, with no console errors. The empty count form is blocked by browser validation (the server validates again). No horizontal scroll at 390 px width. | manual, see README "Screens" |
| Reproducibility | Same seed gives byte-identical files (SHA-256) for every output; a different seed changes them. | `py -3.11 -m data_tools.repro --profile full` |
| Migrations | Empty database → `upgrade head` → `alembic check` reports no drift → `downgrade base` → `upgrade head`. 0004 was applied to the populated full database. | `py -3.11 -m alembic upgrade head; py -3.11 -m alembic check` |
